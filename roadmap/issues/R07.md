## 🎯 Objetivo

Definir a arquitetura operacional do projeto: começar com um binário Go (gateway + world + auth) sobre PostgreSQL, e evoluir para multi-shard, eventos e K8s só quando houver necessidade real. O briefing pedia microsserviços + Kafka + K8s + mesh + Jaeger desde o dia 1; isso é risco disfarçado de escopo.

---

## 📦 Entregáveis

1. **Monólito modular**: gateway + world + auth em um binário Go; PostgreSQL; um processo.
2. **Multi-shard**: separar gateway (stateless) de world (shard por mapa); Redis para sessão/presença; NATS JetStream para eventos.
3. **Eventos**: NATS JetStream (mais simples que Kafka) para analytics/drops/replay; Kafka só se o volume justificar.
4. **Observabilidade**: Prometheus + OpenTelemetry desde o estágio 1 (barato); Jaeger distribuído até haver >1 serviço.
5. **Plataforma**: Docker + Compose; K8s só com múltiplos shards reais; Helm/Terraform prematuros adiados.

## 🧠 Riscos e limites

- **Microsserviços cedo demais**: cada peça adiciona um modo de falha e retrabalho antes de haver sessão jogável.
- **Kafka antes do volume**: Kafka precisa de volume real para justificar; NATS JetStream resolve pub/sub + persistência + replay com uma ferramenta.
- **K8s antes do problema**: K8s antes do problema é infraestrutura como substituto de escopo — vai morrer no caminho.
- **Go ou Rust?**: Go para gateway e serviços, com pontos críticos isolados e benchmarkados (codec, pathfinding); Rust é justificável se a equipe já o domina; não é justificável só por "performance" num jogo de tick de 100–250 ms.
